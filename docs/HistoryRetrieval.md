# Stored-band history and gaps

Live receipt and stored-history transfer are separate capabilities. A worn band and current HR do not prove that earlier readings reached the phone or were stored in band flash. No invented samples or interpolation fill chart gaps.

WHOOP4: subscribe to documented custom channels, confirmed battery query, then application-version query7. Only a successful68-byte revision1 application reply reporting41.17.6.0 enables experimental command22/body00. Standard DIS firmware alone never enables it. START/END/COMPLETE and v24/v25 remain different records. Per-channel bounded reassembly rejects discarded bytes before any ACK; END with unresolved bytes on any subscribed channel is rejected conservatively rather than acknowledging an omitted partial frame. Unknown sensor layouts remain raw, never guessed metrics. The experimental v24 zero-contact flag preserves the measured value but excludes it from analytics; it is not promoted to verified off-body status. This prevents an uncertain charging-band reading filling a worn band’s gap.

A chunk permits at most2MiB/10,000 data frames; its closing END metadata is retained too. Its decoded observations, rejected-layout frames, all raw frames and original8-byte token commit atomically with FULL/WAL durability. Chunk decoding runs off the main actor; storage remains actor-owned. Recent backfill is labelled recent, never a live stream. Ordinary command23 receipt ACK uses01 plus that exact token only after commit, scoped to the same connection/session/dataset. This can permit reclamation of copied band data; forced trim/erase/reset commands are excluded. Empty/incomplete/special-token/damaged chunks cannot be acknowledged. Retries retain IDs; duplicate END handling only acknowledges an already committed token. COMPLETE does not commit an open chunk or prove gap-free coverage.

Each connection reads metadata once; supported W4 retrieval starts automatically after version confirmation and retries on foreground/live snapshot checks when15minutes old. Manual refresh requests a fresh attempt unless one is active. Transfers stop locally after120seconds; a bounded abort20 does not trim uncommitted data. Background wakeups remain subject to iOS. A finite background assertion protects chunk storage, not continuous execution. Force-quit and unvalidated firmware can leave gaps. Reconnect replay and oldest retained date require physical testing. A connection uses at most250 command sequences before reconnect is needed, avoiding unproven sequence-wrap reuse.

Parse the65-byte semantic response plus its two zero padding bytes; refusal/timeout/zero estimates never imply recovered data. A positive estimate starts experimental22/body00. Independently evidenced W5/type49 END token21..<29 is retained exactly. The same bounded durability lifecycle stores original frames, mapped R18 primary HR and checkpoint before ordinary23 ACK. R18 opaque quality/cardio flags stay inspectable as qualityContext; wear remains unknown and raw RR is excluded from HRV. Unknown records remain raw for future reanalysis/backup. Repeated records use device/record-index/timestamp identity; both generations remain separated in raw archives and imports.

The current [Noop12.0 report](https://github.com/ryanbr/noop/releases/tag/v12.0.0) describes some independent pairing contexts that cannot store/offload history. That is not diagnosis of the owner's band. Tempo does not clock-write, enable sensors, transfer certificates, bypass authentication or change firmware. If the band returns no backlog or invalid dates, the app cannot reconstruct missing readings. The owner showed firmware50.42.1.0; no physical history transfer success is yet established.

A connection/session, transfer-attempt UUID and original token scope asynchronous commit callbacks. A late callback from an earlier attempt cannot acknowledge or abort a retry even when its token repeats. Once a valid START arrives, command22 is no longer interrupted by the ordinary20-second reply wait; the finite120-second transfer deadline still applies. Complete/error/abort clears its pending request so a missing command reply cannot block retry. None of these software safeguards proves a physical transfer succeeded.
